# ORISO-managed SigNoz observability

This runbook provisions and proves the ORISO dashboards, alerts, and Slack
delivery route supported by SigNoz `v0.135.1`. It is deliberately separate
from the active OTLP/ClickHouse acceptance in
`runbooks/signoz-runtime-acceptance.md`: both gates must pass.

## What the release owns

The post-install/post-upgrade Job `caritas-signoz-observability` idempotently
creates or updates:

- `ORISO Live Chat and Matrix`: demand, routing, Redis availability, room
  encryption, Matrix processing, push, and notification outcomes;
- `ORISO Service Reliability`: provisioning compensation, dependency calls,
  retries, and replica-safety constraints;
- `ORISO Kubernetes and SigNoz Health`: collector freshness, pod/node health,
  and ClickHouse PVC capacity;
- six active alerts for incomplete compensation, Redis failure, notification
  failure, unencrypted rooms, low ClickHouse capacity, and stale collector
  telemetry;
- one Slack notification channel and the rule routes generated by SigNoz.

All names are environment-specific. Every query has a fixed
`deployment.environment` filter; infrastructure queries also have a fixed
`k8s.cluster.name` filter. Dashboard variables are intentionally absent, and
alert grouping is limited to the static `environment` label.

## Preflight

Do not deploy this child before the reviewed ClickHouse RBAC, Kubernetes
collector, and UserService diagnostic-metrics PRs are merged into `pre-dev`.
Confirm the runtime image digests separately; a merged chart is not deployment
evidence.

Create an admin-role SigNoz service account and API key. Store that key and the
Slack incoming-webhook URL in the environment's secret-management workflow as:

```text
Secret: caritas-signoz-observability
Keys:   apiKey, slackWebhookUrl
```

The webhook chooses the Slack destination; the chart does not hard-code or
override a channel. Never put either value in Helm values, a GitHub secret
comment, terminal output, or this repository.

Verify key names without reading their values:

```bash
kubectl -n caritas get secret caritas-signoz-observability \
  -o go-template='{{range $key, $value := .data}}{{$key}}{{"\n"}}{{end}}'
```

Expected output contains exactly `apiKey` and `slackWebhookUrl`. The API key
must authenticate successfully as an administrator; a wrong role fails fast
instead of retrying for the full readiness timeout.

## PreDev release and proof

Render before applying:

```bash
helm template caritas . -n caritas \
  -f values.yaml.default -f secrets.yaml -f values-pre-dev.yaml \
  > /tmp/oriso-predev-rendered.yaml
```

Apply only through the normal reviewed PreDev release workflow. The hook waits
for the SigNoz API, upserts the managed assets, sends one contextual route-test
notification, executes every dashboard and alert query, requires fresh
`pre-dev`/`oriso-predev` collector data, and fails if `dev`/`oriso-dev` data is
visible.

Read the retained evidence:

```bash
kubectl -n caritas wait --for=condition=complete \
  job/caritas-signoz-observability --timeout=15m
kubectl -n caritas logs job/caritas-signoz-observability
```

The final line must start with:

```text
PASS: SigNoz dashboards, alerts, routes, queries, freshness, and environment separation for pre-dev
```

Then run the active ingestion gate from `runbooks/signoz-runtime-acceptance.md`.
That gate emits and reads back a synthetic correlated trace, metric, and log and
proves Kubernetes signal breadth and log-body suppression. In the SigNoz UI,
open all three ORISO dashboards and confirm that the tested Slack destination
received the route-test message with environment and cluster context.

## Dev promotion

Promote only the reviewed commits that passed PreDev. Repeat the same gates
with `values-dev.yaml`. The hook must require fresh `dev`/`oriso-dev` collector
data and reject any visible `pre-dev`/`oriso-predev` data. The expected final
line ends in `for dev`.

Do not call the work live or complete until chart ancestry, deployed images,
Job evidence, active ingestion, SigNoz UI, and Slack delivery have each been
verified on Dev.

## Read-only recheck

The same program supports `--mode check`, which performs no dashboard, alert,
channel, or route writes and sends no notification. Run it from a short-lived
copy of the retained Job after changing its argument from `provision` to
`check`, or execute the checked-in script from an approved operator context
with the same five non-secret identity inputs and service-account key.

The check fails on missing/obsolete/disabled assets, unbounded grouping,
protected identifier fields, unresolved placeholders, failed queries, missing
routes, stale local collector telemetry, or cross-environment telemetry.

## Rollback

Re-deploy the last reviewed chart revision. If alert noise itself is the
incident, disable the six `ORISO <environment> | ...` rules in SigNoz before
changing or removing the channel; retain the dashboards and Job logs as
evidence. Setting `signoz.orisoObservability.enabled=false` stops future hook
runs but intentionally does not delete server-side dashboards, rules, routes,
or channels.

Do not delete the Secret during rollback. Rotate its API key or webhook through
the normal secret-management process if either credential may be exposed.
